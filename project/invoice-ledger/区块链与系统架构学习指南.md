# 从发票应用理解区块链与软件架构

> 阅读目标：读完本文后，你应该能解释“为什么本项目需要 Docker 和 Fabric”“一次存证从浏览器到区块链经历了什么”“链上数据为什么难以篡改”，并能在答辩时清楚介绍项目架构。

---

## 1. 先用一句话理解本项目

“链证发票”是一个网页应用：用户在浏览器录入发票，后端将数据摘要和关键字段提交到 **Hyperledger Fabric 联盟链**；之后任何人都可以查询发票当前状态、流转记录和历史交易，并用内容哈希核验发票是否被改动。

它不是“自己发明一条区块链”，而是把 Hyperledger Fabric 这一套已经实现共识、身份、账本和智能合约的区块链平台，用在“发票管理”场景。

```text
用户填发票
    ↓
浏览器页面（前端）
    ↓ HTTP / JSON
Go 后端（业务校验、计算哈希、调用 SDK）
    ↓ gRPC / X.509 证书签名
Fabric 网络（Peer、Orderer、CA、智能合约）
    ↓
区块账本 + 当前世界状态
```

---

## 2. 区块链到底解决了什么问题？

### 2.1 普通数据库的模式

在普通 Web 系统中，发票通常保存在某个企业自己的 MySQL、PostgreSQL 或 Excel 中：

```text
浏览器 → 企业后端 → 企业数据库
```

这很高效，但有一个信任前提：所有人都要相信数据库管理员和拥有该数据库的企业。管理员理论上可以直接修改一行数据，或者删除一条历史记录；其他企业也不容易独立验证。

### 2.2 区块链的模式

区块链把“谁可以写入、写入什么、历史如何保留”变成一套多方共同遵守的规则。每笔交易由身份签名、多个节点背书、排序后写进区块。每个参与节点保存账本副本。

它的价值不是“数据永远绝对正确”。如果一开始录入的销售方或金额就是假的，区块链不会自动识别。它保证的是：**一旦按规则确认上链，之后很难悄悄修改，且能追溯是谁、何时、通过哪笔交易改变了状态。**

### 2.3 为什么发票适合这个场景

发票会在开票方、购买方、报销方、财务人员、审计人员之间流转，常见问题包括：

- 展示的电子发票是否与原始发票一致；
- 这张发票当前由谁持有；
- 是否发生过异常流转或重复流转；
- 发生争议时能否还原完整处理过程。

本项目正好以“存证—流转—核验”回答这三个问题。

## 3. 三个容易混淆的概念

### 3.1 区块（Block）

区块可以理解成“按时间打包的一页交易记录”。它里面有多笔交易、前一个区块的哈希等信息。新区块会引用前一区块的哈希，形成链式结构。

如果有人事后修改旧区块的一笔交易，旧区块哈希会变化，后续区块中保存的“前一区块哈希”就对不上。因此，修改历史不仅要改一处，还要重新获得网络认可，成本很高。

### 3.2 交易（Transaction）

交易是一次被区块链记录的业务操作，不一定是“转账”。在本项目中，下列都是交易：

- 创建发票存证：`CreateInvoice`；
- 将发票从 A 流转到 B：`TransferInvoice`；
- 查询或核验：通常是只读调用，不会写入新区块。

每笔写入交易都有一个唯一 `TxID`。在页面详情的“链上历史”中可以看到交易 ID 的前半部分。

### 3.3 哈希（Hash）

哈希函数会把任意长度的数据变成固定长度的“指纹”。本项目使用 SHA-256，结果是 64 位十六进制字符串，例如：

```text
0f8a...（共 64 个十六进制字符）
```

哈希有三个适合存证的特性：

1. 相同输入一定得到相同输出；
2. 原始内容哪怕只改一个字符，结果也会完全不同；
3. 由哈希倒推出原始内容在计算上不可行。

因此，我们不必把 PDF/OFD 文件本身放进区块链，也可以把文件或关键字段的哈希上链。以后重新计算待验发票的哈希，再与链上哈希对比即可判断内容是否一致。

## 4. 什么是 Hyperledger Fabric？

Hyperledger Fabric 是面向企业协作的**联盟链**平台。它与比特币、以太坊这类公有链最明显的区别是：加入网络的组织和用户都要先获得许可身份，而不是任何匿名用户都能参与。

### 4.1 为什么课程项目选择 Fabric

发票系统涉及企业、财务或审计机构，往往需要明确身份、权限和隐私边界；也不需要挖矿或公开代币。Fabric 更适合这种“多个已知机构共同维护业务数据”的场景。

### 4.2 本项目中出现的 Fabric 组件

| 组件                | 可以把它理解成                 | 在项目中的作用                       |
| ------------------- | ------------------------------ | ------------------------------------ |
| Peer（对等节点）    | 业务节点 + 账本副本            | 执行发票智能合约、保存账本和世界状态 |
| Orderer（排序节点） | 交易的排队与打包服务           | 将已背书交易排序并写入区块           |
| CA（证书机构）      | 企业身份的“发证机关”         | 为节点和用户生成测试证书             |
| Channel（通道）     | 一条有成员范围的业务账本       | 本项目使用`mychannel`              |
| Chaincode（链码）   | 部署到区块链的业务后端         | 定义存证、流转、核验规则             |
| Gateway SDK         | 普通后端连接 Fabric 的客户端库 | Go 后端通过它提交或查询交易          |

### 4.3 两个组织意味着什么

课程 Test Network 会创建 `Org1` 和 `Org2` 两个组织，各自有一个 Peer。它们可以类比为两家参与发票业务的机构。课程演示使用 Org1 的 `User1` 证书连接网络。

当前代码中的“销售方”“购买方”“当前持有人”是业务字段，用于模拟业务权限；它们不是 Fabric 证书身份本身。生产环境应为每家企业注册 Fabric CA 用户，并由链码读取证书属性来判断权限。

## 附录 A：认识比特币、以太坊与 Fabric

学习区块链时最常遇到的三个名字是**比特币（Bitcoin）**、**以太坊（Ethereum）**和**Hyperledger Fabric**。它们都使用了分布式账本、密码学签名和区块链式历史记录，但目标并不相同。

可以先用一个非常粗略的类比理解：

```text
比特币：     一个让陌生人也能转移原生数字货币的公开账本
以太坊：     一个让陌生人也能运行公开可组合程序的公开计算平台
Fabric：      一套让已知机构之间协作记账、按权限执行业务规则的平台
链证发票：   运行在 Fabric 上的一套具体发票业务应用
```

### A.1 比特币：区块链概念的起点

比特币最初要解决的问题是：没有银行作为中央记账方时，互不认识的人如何在互联网转移一种数字资产，并防止同一笔钱被重复花费（双花）？

它采用公开网络。任何人都可以下载客户端、查看账本、生成地址和发送交易；网络不要求先登记真实姓名。因此，比特币首先是一套**无需中心机构即可达成账本共识的电子现金系统**。

#### A.1.1 地址、私钥和签名

比特币用户通常会看到“地址”，但真正重要的是私钥。

- **私钥**：一串必须秘密保存的随机数据，可以用来为交易签名；谁掌握私钥，谁就能花费对应资产。
- **公钥/地址**：可公开提供给别人，用于接收资产和验证签名。
- **数字签名**：证明交易确实由私钥持有者授权，且交易内容在签名后没有被改动。

这和本项目中 Fabric 用户用 X.509 证书和私钥签名有相似之处：都依赖“私钥签名、公钥验证”。区别在于 Fabric 的身份由组织 CA 管理，比特币地址通常不绑定现实身份。

> 重要安全常识：私钥、助记词和钱包备份不应交给任何人，也不要截图、上传网盘或发送到聊天软件。课程中看到的测试证书仅用于本地实验，不能等同于真实资产钱包。

#### A.1.2 UTXO：比特币如何记录“余额”

比特币并不像银行账户那样直接在链上保存“张三余额 = 100”。它使用 UTXO（Unspent Transaction Output，未花费交易输出）模型。

可以把每个 UTXO 想成一张可花费的电子钞票。它来自此前某笔交易的输出，在下一次被引用并花费之前一直存在。

例如：

```text
Alice 拥有一个 10 BTC 的 UTXO
Alice 想支付 Bob 3 BTC

新交易：
输入：花费 Alice 的 10 BTC UTXO
输出 1：3 BTC → Bob
输出 2：6.999 BTC → Alice（找零）
手续费：0.001 BTC
```

原来的 10 BTC UTXO 一旦被花费就不能再次使用。节点会验证它是否确实未花费、签名是否正确、输入金额是否不小于输出金额；这就是防止双花的关键之一。用户看到的“余额”，本质上是其可控制的所有 UTXO 的金额总和。

这与本项目的发票模型不同：发票是一个有唯一 ID、可更新当前持有人的业务对象，更接近“状态对象”；比特币的 UTXO 则更接近“不可拆回的票据集合”。

#### A.1.3 工作量证明与挖矿

比特币网络早期和长期使用工作量证明（Proof of Work，PoW）来决定谁有资格提议新区块。矿工不断尝试计算满足难度条件的哈希，最先找到有效结果的一方可以发布区块，其他节点验证其有效性后接受它。

工作量证明的核心作用不是“做无意义计算”，而是让篡改历史需要付出昂贵的计算成本。若想重写某个旧区块后的历史，攻击者需要重新完成足够多的工作量，并持续超过诚实网络的算力。

但它也带来代价：公开网络中的 PoW 消耗能源、确认时间较长、吞吐量有限。因此它适合去中心化价值转移，不一定适合企业内部高频业务系统。

#### A.1.4 比特币脚本与“智能合约”

比特币并非完全不能编程。它有一种受限的 Script 脚本语言，可表达“需要多方签名才能花费”“在某时间后才能花费”等规则。

但比特币的设计重点是安全、简单的货币转移，而不是运行复杂业务程序。它的脚本通常不支持像普通应用那样任意循环和复杂状态，因此不适合直接实现本项目这种发票列表、持有人、流转事件等丰富业务对象。

### A.2 以太坊：可编程区块链

以太坊将区块链从“主要记录货币转账”扩展为“可以在链上运行通用业务逻辑”。它提出了智能合约和 EVM（Ethereum Virtual Machine，以太坊虚拟机）的概念。

在以太坊中，开发者通常用 Solidity 等语言编写合约，部署到链上；合约部署后获得一个地址，用户可向该地址发送交易调用其中的函数。

```text
用户钱包
   ↓ 签名交易
以太坊节点 / EVM
   ↓ 执行 Solidity 编译后的字节码
合约状态更新 + 事件日志 + 区块记录
```

#### A.2.1 两类账户

以太坊常见的账户类型有两类：

| 账户类型            | 控制方式       | 例子                      |
| ------------------- | -------------- | ------------------------- |
| EOA（外部拥有账户） | 由用户私钥控制 | 用户钱包地址              |
| 合约账户            | 由合约代码控制 | ERC-20 代币合约、NFT 合约 |

EOA 可以发起交易；合约账户本身没有人类私钥，它会在被交易调用时按既定代码执行。比如一个代币合约可维护“地址 → 余额”的映射，并实现转账、授权等函数。

#### A.2.2 EVM 和确定性执行

EVM 是所有以太坊节点都遵循的虚拟执行环境。同一笔交易的合约代码必须在不同节点上得到相同结果，否则无法达成共识。

因此 Solidity 合约也不能随意读取外部网页、调用不确定的随机数或依赖某台机器的本地文件。这一点与 Fabric 链码的确定性要求完全一致。

现实世界信息若要进入链上，通常需要通过“预言机（Oracle）”提供并经额外机制验证。例如汇率、天气或税务状态都不是区块链节点天然知道的数据。

#### A.2.3 Gas：为什么调用合约要付费

以太坊上执行每条指令都需要消耗 Gas。用户为交易设定可用 Gas 和愿意支付的 Gas 价格，最终用原生货币支付执行费用。

Gas 主要解决两件事：

1. 防止有人提交无限循环或极其耗资源的程序，拖垮所有节点；
2. 为验证和打包交易的网络参与者提供经济激励。

读取公开数据通常可以由节点本地模拟，不一定需要真正提交交易；但改变合约状态必须成为链上交易，因此需要费用。你在发票项目中没有看到 Gas，是因为课程使用的 Fabric Test Network 不采用这种面向公开网络的手续费机制。

#### A.2.4 合约状态、事件与 DApp

以太坊合约可保存状态变量，例如：

```solidity
mapping(address => uint256) balances;
```

也可以发出 Event（事件日志），让前端或索引服务订阅。一个典型 DApp（去中心化应用）通常包含：

```text
浏览器前端 → 钱包插件签名 → RPC 节点 → 以太坊智能合约
```

与本项目最大的架构差异是：很多以太坊 DApp 会让用户钱包在浏览器端签名；而 Fabric 企业系统通常由后端保管并使用组织证书连接网络。这是由“公开匿名网络”和“受控企业网络”的身份模型不同造成的。

#### A.2.5 常见的以太坊应用概念

- **ERC-20**：一套同质化代币接口规范，例如积分或项目内代币。
- **ERC-721 / ERC-1155**：常用于 NFT（非同质化代币）等唯一或半同质资产。
- **DeFi**：去中心化金融，指在智能合约上实现兑换、借贷等金融协议。
- **NFT**：链上唯一代币及其所有权记录；它不等于图片文件本身，图片常在链下存储。

这些概念用于理解技术生态即可，不代表本项目需要引入代币、NFT 或金融功能。发票管理更关注企业身份、隐私和审计，因此 Fabric 更合适。

### A.3 三种平台的关键区别

| 维度         | 比特币                 | 以太坊                               | Hyperledger Fabric（本项目）             |
| ------------ | ---------------------- | ------------------------------------ | ---------------------------------------- |
| 网络类型     | 公有、开放参与         | 公有、开放参与                       | 联盟链、成员准入                         |
| 主要目标     | 去中心化电子现金       | 可编程公开区块链                     | 企业/机构协作业务                        |
| 身份方式     | 地址，通常匿名或假名   | 地址，通常匿名或假名                 | CA 证书、组织 MSP                        |
| 数据模型     | UTXO                   | 账户与合约状态                       | 世界状态 + 区块账本                      |
| 业务代码     | 受限 Script            | EVM 合约（常用 Solidity）            | Chaincode（本项目使用 Go）               |
| 共识特点     | 工作量证明             | 公共验证者共识机制                   | 已知组织间的背书、排序与提交             |
| 手续费       | 交易手续费             | Gas                                  | 通常由联盟规则决定，不必面向公开市场收费 |
| 数据可见性   | 高度公开               | 高度公开                             | 可按通道、组织、私有数据控制             |
| 本项目适配性 | 不适合复杂企业发票管理 | 可以实现，但公开性和费用模型未必合适 | 适合                                     |

### A.4 为什么本项目不用比特币或以太坊？

不是因为它们“不好”，而是技术选型要匹配场景。

1. 发票业务的参与者通常是已知企业和机构，需要证书身份与角色权限；
2. 发票可能包含企业名称、金额等不希望对全网公开的信息；
3. 课程要求明确规定区块链层使用 Hyperledger Fabric；
4. 本项目需要灵活的 Go 业务链码、快速的本地开发和可控的测试网络。

若题目变成“面向所有陌生用户发行可自由交易的数字藏品”，以太坊可能是更自然的选择；若题目是“无需机构参与的全球点对点价值转移”，比特币的设计目标更接近需求；而“多家已知企业协同核验发票”则正是 Fabric 的典型应用。

### A.5 把知识串起来

你可以用下面这段话概括三者关系：

> 比特币证明了无需中心机构也能在公开网络中维护不可重复花费的价值账本；以太坊进一步让区块链能够承载通用智能合约；Hyperledger Fabric 则针对企业协作场景，采用许可身份、通道和链码机制。我们的发票系统基于 Fabric，将存证、流转和核验规则写入链码，以获得可追溯、难篡改且适合多机构协作的业务账本。

## 5. 为什么需要 Docker？

Fabric 不是一个单独的可执行文件。运行网络时至少会有 Peer、Orderer、CA 等多个服务，它们各自有依赖和配置。Docker 将每个服务装入一个隔离容器，使课程环境能够一键启动：

```text
Docker 容器
├── peer0.org1.example.com
├── peer0.org2.example.com
├── orderer.example.com
├── ca_org1
├── ca_org2
└── ca_orderer
```

课程中的 `test-network/network.sh` 会调用 Docker 和 Docker Compose 创建这些容器、生成证书、创建通道。你的 Go 后端不在 Docker 中运行，但它需要连接其中的 `peer0.org1`，所以 Fabric 容器必须先启动。

## 6. 智能合约（Chaincode）是什么？

智能合约不是“有意识的程序”，它就是部署到区块链上的确定性业务代码。在 Fabric 中，智能合约通常称为 Chaincode（链码）。

本项目的链码文件是：

```text
chaincode/invoice_contract.go
```

它定义了哪些操作可被写入账本，以及执行前要满足的规则。

| 链码函数              | 业务含义                       | 是否写入账本 |
| --------------------- | ------------------------------ | ------------ |
| `CreateInvoice`     | 创建一张发票并生成首次开具记录 | 是           |
| `TransferInvoice`   | 从当前持有人转给下一持有人     | 是           |
| `ReadInvoice`       | 查询一张发票当前状态           | 否           |
| `GetAllInvoices`    | 查询所有发票                   | 否           |
| `GetInvoiceFlows`   | 查询流转事件                   | 否           |
| `VerifyInvoice`     | 比较提交的哈希与链上哈希       | 否           |
| `GetInvoiceHistory` | 查询该发票每次状态变化         | 否           |

### 6.1 为什么链码必须“确定性”

多个 Peer 需要对同一笔交易执行同样的链码并得出同样结果。若链码随意调用本地随机数、访问外部网页或读取本机时间，就可能出现不同节点结果不同，导致交易无法被认可。

本项目需要时间时使用交易中携带的时间戳 `GetTxTimestamp()`，而不是直接使用服务器当前时间；这正是为了保证不同节点的结果一致。

### 6.2 链码中的关键校验

`CreateInvoice` 会检查：

- 发票 ID、号码、参与方等关键字段不能为空；
- 发票 ID 不能与已有记录重复；
- 操作人必须与销售方一致；
- 金额和税额以非负整数“分”保存；
- 内容哈希必须为 64 位。

`TransferInvoice` 会检查：

- 转出方必须是链上记录的当前持有人；
- 操作人必须是转出方；
- 转出方和接收方不能相同。

因此，不能直接把一张由 A 持有的发票伪装成由 B 转出。

## 7. 账本、世界状态和历史记录有什么区别？

这是 Fabric 最重要的概念之一。

### 7.1 区块账本（Blockchain Ledger）

账本保存每一笔已提交交易的完整时间顺序，它是“总账”和审计证据。写入之后不应被删除或改写。

### 7.2 世界状态（World State）

世界状态是当前最新业务数据的快速索引，可以理解为从整个账本中计算出的“当前快照”。

例如一张发票先由“云帆公司”持有，后转给“北辰公司”：

```text
历史账本：开具给云帆 → 云帆转给北辰
世界状态：当前持有人 = 北辰
```

页面“发票账本”列表查询的是世界状态，因此读取很快；页面“链上历史”查询的是同一个发票键的历史变更，因此能看到每次转手。

### 7.3 为什么还要单独保存流转事件

本项目除了更新 `Invoice.CurrentHolder`，还为每次流转创建独立 `InvoiceFlow` 记录。这样做有两个好处：

1. 查询流转时间线时不必解析所有历史状态；
2. 每个流转事件含转出方、接收方、操作人、交易 ID 和时间，业务表达更清楚。

```text
INVOICE#INV-001                  → 当前发票状态
FLOW#INV-001#交易ID-开具          → 第一次开具事件
FLOW#INV-001#交易ID-流转          → 后续流转事件
```

## 8. 从“点击存证”到“上链成功”的完整流程

下面是你在页面提交一张发票时实际发生的事情。

### 第 1 步：前端收集与转换数据

网页文件在 `web/`。用户填入发票号码、销售方、购买方、金额等字段。前端将“元”转换成整数“分”，例如 `100.50 元` 变成 `10050 分`。

用分而不用浮点数很重要：计算机中的 `0.1 + 0.2` 在某些语言中可能不是精确的 `0.3`，而整数加法没有该问题。

### 第 2 步：浏览器调用 REST API

前端 JavaScript 向后端发送请求：

```http
POST /api/invoices
Content-Type: application/json
```

请求中只包含业务数据。浏览器不会直接连接 Fabric，因为浏览器不应持有企业证书私钥，也不适合处理区块链网络连接。

### 第 3 步：后端生成内容哈希

后端文件 `backend/api/invoice.go` 按固定顺序拼接关键字段：

```text
发票号码|开票日期|销售方|购买方|金额（分）|税额（分）|价税合计（分）|币种
```

再计算 SHA-256，得到 `dataHash`。固定字段顺序很关键：如果同样数据的拼接顺序不同，就会得到不同哈希。

### 第 4 步：Gateway SDK 签名并提交交易

后端的 `backend/fabric/gateway.go` 读取 Org1 的 X.509 证书和私钥，创建 Fabric Gateway 连接。提交交易时，SDK 会使用私钥签名，证明“这是持有该身份的一方发出的请求”。

### 第 5 步：Peer 背书

Peer 收到 `CreateInvoice` 调用后执行链码。它先检查规则，再模拟写入结果。满足背书策略时，Peer 对结果签名。

### 第 6 步：Orderer 排序、形成区块

后端将已背书交易提交给 Orderer。Orderer 不判断具体业务对错，它负责给交易排顺序、打包成区块，并分发给通道中的 Peer。

### 第 7 步：Peer 提交账本并更新世界状态

每个 Peer 验证区块与背书后，将区块追加到本地账本，并将 `INVOICE#发票ID` 的最新状态写入世界状态。后端收到提交成功结果后，返回“发票已完成链上存证”。

```text
浏览器 → POST /api/invoices → Go 后端
       → Gateway 签名 → Peer 执行链码 / 背书
       → Orderer 排序打包 → Peer 提交区块
       → 后端响应成功 → 浏览器刷新发票列表
```

## 9. 查询、流转、核验分别怎么工作？

### 9.1 查询发票

浏览器调用 `GET /api/invoices`，后端使用 Gateway 的 `EvaluateTransaction("GetAllInvoices")` 调用链码。这类调用只读取世界状态，不生成新区块，也不需要等待排序。

### 9.2 发票流转

页面详情中填写“下一持有人”并提交。后端调用 `TransferInvoice`。链码读取当前发票，确认 `from` 与 `CurrentHolder` 相同后：

1. 更新发票的当前持有人和状态；
2. 新建一条 `InvoiceFlow`；
3. 作为一笔新的 Fabric 交易提交。

因此，流转不是简单修改前端显示文字，而是一次可追溯的链上状态变化。

### 9.3 内容核验

核验人将发票 ID 和内容哈希提交到 `POST /api/invoices/:id/verify`。链码读取该 ID 对应的 `Invoice.DataHash`，与用户提供的哈希进行比较。

```text
待验内容重新计算得到的哈希 == 链上 DataHash  → 通过
待验内容重新计算得到的哈希 != 链上 DataHash  → 不通过
```

演示时可以使用新建存证后系统返回的哈希做一次“通过”核验，再把最后一个字符改掉做一次“不通过”核验。这是最直观的区块链存证展示。

## 10. 本项目的软件目录与职责

```text
invoice-ledger/
├── web/                         前端页面：用户看见和操作的部分
│   ├── index.html               页面结构
│   ├── styles.css               视觉样式
│   └── app.js                   调用 REST API、更新列表和详情
├── backend/                     应用后端：连接网页与 Fabric 的桥梁
│   ├── main.go                  启动 HTTP 服务、托管网页
│   ├── api/invoice.go           REST 接口、哈希计算、请求校验
│   └── fabric/gateway.go        读取证书并通过 Gateway SDK 连接 Fabric
├── chaincode/                   智能合约：链上的核心业务规则
│   ├── main.go                  启动链码
│   └── invoice_contract.go      发票数据模型与交易函数
├── scripts/                     本地启动与部署脚本
│   ├── start-network.sh         启动 Docker 中的 Fabric 网络
│   ├── deploy-chaincode.sh      打包、安装、批准、提交链码
│   └── start-app.sh             启动 Go 后端和网页服务
└── *.md                         实现说明、答辩材料和学习资料
```

这是一种典型的分层 B/S 架构：

- **表现层**：`web/`，负责界面与交互；
- **应用层**：`backend/`，负责 HTTP、输入校验、哈希、权限接入和 SDK 调用；
- **区块链业务层**：`chaincode/`，负责所有必须被共同信任的规则；
- **数据层**：Fabric 的账本和世界状态。

把业务规则只写在前端是不安全的，因为用户可以绕过网页直接构造请求；把关键规则放在链码中，才会让所有参与节点共同执行。

## 11. 证书、MSP 与权限：为什么不能把私钥放到前端

Fabric 使用 PKI（公钥基础设施）管理身份。每个参与者通常拥有：

- **证书**：类似公开的身份证明，其他人用它验证签名；
- **私钥**：类似签名用的印章，只能由本人保管；
- **MSP**：成员服务提供者，定义一个组织信任哪些 CA 和证书。

当前后端读取 Test Network 的以下测试身份：

```text
organizations/peerOrganizations/org1.example.com/
users/User1@org1.example.com/msp/
```

浏览器端任何人都能查看网页脚本，若把私钥放到浏览器，就等于把企业印章公开。因此私钥只在后端受控环境使用，前端通过 HTTPS/HTTP 调用后端接口。

课程项目中用“操作人等于当前持有人”等字段校验模拟业务权限。真正企业系统还应做到：

1. 每个企业和用户由 CA 单独注册；
2. 链码根据调用者证书读取组织与角色；
3. 不同角色只能调用允许的交易；
4. 重要操作保留审批和审计记录。

## 12. 常见误解与答辩可用表述

### 误解一：上链就是把所有数据公开

不是。Fabric 是许可网络，通道只对成员组织开放；生产系统还可使用私有数据集合。即使如此，附件原文通常也应放对象存储或 IPFS，链上保存哈希、索引和必要业务字段。

### 误解二：区块链上的数据永远不能改变

更准确地说：**历史记录不可被悄悄抹去，但当前状态可以通过新的合规交易改变。**

例如发票作废不应直接删除旧发票，而应新增“作废”交易，将状态更新为 `VOIDED`，历史仍能证明它曾经被开具、何时作废、由谁操作。

### 误解三：有区块链就不需要后端

不是。后端仍负责账号会话、输入校验、文件处理、哈希计算、与企业系统集成和安全保管私钥。区块链只承担适合多方共同确认和审计的那部分核心状态。

### 误解四：哈希相同就证明发票真实合法

哈希相同只能证明“当前待验内容与当初存证内容一致”。它不能替代税务机关对开票资格、交易真实性的业务审核。答辩时应清楚区分“内容完整性证明”和“业务真实性审核”。

### 推荐答辩总结

> 我们采用 Fabric 联盟链保存发票关键字段、内容哈希和流转事件。链码保证只有符合当前持有人规则的操作才能改变状态；账本历史保证后续操作可追溯。前端负责交互，Go 后端负责哈希计算和 Gateway SDK 接入，Docker 负责运行本地 Fabric 网络。该方案解决的是多方协作下发票数据的防篡改、可追溯和可核验问题。
