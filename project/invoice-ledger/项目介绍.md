## 一、项目概述

本项目面向学校、总部或科研项目管理场景，设计并实现了一套基于 **B/S 架构 + Hyperledger Fabric 联盟链** 的项目管理与发票报销应用。系统以“项目立项—项目执行—发票存证—跨组织交接—报销审核—财务支付—结项验收”为主线，将关键业务数据、状态变化和操作痕迹写入 Fabric 账本，实现可查询、可追溯、难以事后篡改的业务记录。

系统并非仅展示区块链概念，而是提供可在浏览器直接操作的完整应用：用户可登记业务组织、注册不同岗位的成员、申请项目、录入或 OCR 识别发票、创建报销单、进行审核与支付，并在详情页查看链上流转和历史记录。

## 二、拟解决的实际问题

传统项目报销通常依赖纸质票据、Excel 表格、聊天记录或集中式数据库，容易产生以下问题：

1. **票据真实性与一致性难核验**：发票内容在录入、传递或汇总过程中可能被误填，缺少便捷的内容比对机制。
2. **交接责任不清晰**：发票在项目组、合作单位、财务人员之间流转时，难以准确确认“何时由谁交给谁”。
3. **项目经费过程不透明**：预算、冻结额度和已支付金额分散记录，容易发生重复报销或超预算风险。
4. **审核过程缺乏可审计依据**：立项、结项和报销审核意见若仅保存于普通系统，后续难以证明其未被修改。
5. **多组织协作缺少共同可信账本**：主体单位、内部项目组和外部财务/合作单位之间需要共享部分可信记录，但又不希望完全依赖任一方的私有数据库。

针对上述问题，本项目采用 Fabric 联盟链保存关键业务状态和证据摘要，以智能合约约束操作顺序与权限，实现“业务流程可执行、关键结果可验证、责任变化可追溯”。

## 三、应用场景与产品方案

### 3.1 典型场景

以“学校科研项目经费管理”为例：

```text
学校/总部（主体组织）
  └─ 项目组（内部项目组）提交项目申请和发票
       ↓
项目管理审核员审核立项、结项与报销材料
       ↓
财务协作组织确认支付
       ↓
必要时，跨组织流转员负责票据交接与责任留痕
```

系统同样可扩展到企业总部—部门项目组—财务共享中心、甲方—供应商—审计机构等需要票据、预算和审批记录协同管理的场景。

### 3.2 两层组织模型

为避免混淆业务组织与 Fabric 技术组织，系统区分两层概念：

- **业务组织**：在网页中登记，包含主体组织、公司内部项目组、外部协作组织。它们用于表达真实业务归属和组织层级，并作为用户注册时的所属组织。
- **Fabric 技术组织**：当前课程测试网络使用 `Org1MSP` 和 `Org2MSP` 两个组织、两个 Peer 节点。业务组织会绑定其中一个接入节点，系统据此选择对应组织的测试证书提交交易。

因此，网页新增一个外部协作组织并不等于自动创建新的 Fabric Peer 或 CA；真正新增联盟链成员仍需要完成证书签发、Peer 部署、通道加入与背书策略更新等网络运维操作。

## 四、系统功能设计

### 4.1 业务组织与成员管理

- 组织管理员可登记主体组织、内部项目组和外部协作组织；内部项目组必须关联一个主体组织。
- 新用户注册时从组织目录中选择所属业务组织，系统自动绑定对应 Fabric 接入节点。
- 点击组织卡片可查看该组织已绑定成员、账号、岗位和底层节点信息。

### 4.2 项目申请、审核与资金池

- 项目组成员创建项目草稿，填写项目名称、内容、预算和预期结项日期。
- 项目提交后由项目管理审核员选择“通过”或“要求修改”，并填写审核意见。
- 立项通过后，预算初始化为项目资金池可用额度。
- 项目组可提交结项材料说明，审核员完成结项审核。
- 系统记录可用额度、冻结额度和已支付金额，防止超预算支付。

### 4.3 发票存证、OCR 与核验

- 支持手动填写发票号码、日期、销售方、购买方、金额、税额、币种和关联项目。
- 支持上传或拖拽图片/PDF，调用阿里云 OCR 统一识别服务进行辅助回填；OCR 结果须由用户人工确认后才可上链。
- 后端按稳定字段顺序计算 SHA-256 内容指纹，将发票要素、指纹、当前责任人和首次存证记录写入 Fabric。
- 用户可在详情页一键填入核验中心，验证输入指纹是否与链上存证一致。

### 4.4 发票流转、作废与作废申请

- 发票创建后记录当前责任人和其所属 Fabric 组织。
- 当发生跨组织票据交接时，当前责任人可将发票交给已注册的跨组织流转员；链上保存交接双方、组织、时间和交易 ID。
- 开票员可直接作废本组织开具的发票，并填写原因。作废不会删除原记录，而是追加一笔作废状态交易；已作废发票不能用于报销。
- 项目组成员可对“本人申请的项目”关联发票提交作废申请；申请原因、申请人和时间写入链上，但此时发票仍保持原状态。
- 开票员可在发票详情中审核申请：批准后才将发票变更为“已作废”；驳回时保留发票并记录审核意见。项目成员可补充原因后再次申请。

### 4.5 报销审核与财务支付

- 项目申请人只能从当前项目下、未作废且未重复报销的发票中选择报销对象。
- 报销审核通过时，发票总金额从项目可用额度转为冻结额度。
- 财务管理员确认支付后，冻结额度转为已支付金额。
- 同一发票不可关联多个报销单，项目资金池不足时智能合约拒绝审核通过。

## 五、角色与权限

| 角色 | 主要权限 |
| --- | --- |
| 组织管理员 | 登记业务组织、查看组织成员。 |
| 项目组成员 | 创建/修改/提交项目，申请结项，存证关联项目的发票，提交报销单；可申请作废本人项目关联的发票。 |
| 项目管理审核员 | 审核立项、结项和报销单，填写审核意见。 |
| 财务管理员 | 对已审核并冻结额度的报销单确认支付。 |
| 开票员 | 创建发票、直接作废本组织开具的发票；审核项目组提交的作废申请。 |
| 跨组织流转员 | 接收或继续交接跨组织流转的发票。 |
| 审计员 | 查询组织、项目、发票、报销单、流转轨迹和链上历史。 |

前端会根据岗位隐藏不相关的操作入口；后端接口和智能合约规则进一步限制关键业务操作，避免仅依赖页面显示进行权限控制。

## 六、技术方案与系统架构

### 6.1 技术栈

| 层次 | 技术选型 |
| --- | --- |
| 前端 | HTML、CSS、JavaScript，单页式侧边栏界面，Notion 风格轻量 UI。 |
| 后端 | Go、Gin，提供 REST API、会话认证、业务校验和 SHA-256 摘要计算。 |
| 区块链 | Hyperledger Fabric 2.5，双组织测试网络、Channel `mychannel`、链码 `invoice` v2.0。 |
| 智能合约 | Go + Fabric Contract API，维护发票、流转、作废申请、用户、组织、项目、资金池和报销单状态。 |
| 链接方式 | Fabric Gateway SDK，根据用户所属业务组织绑定的 MSP 连接 Org1 或 Org2 Peer。 |
| OCR | 阿里云 OCR 统一识别 API；可选接入 AI 纠偏建议。 |
| 容器化环境 | Docker、Docker Compose、Fabric Test Network。 |

### 6.3 链上与链下数据划分

| 数据类别 | 保存位置 | 说明 |
| --- | --- | --- |
| 业务组织、用户归属、岗位 | 链上 | 用于组织目录、角色识别和审计。 |
| 项目状态、预算、资金池变化、审核意见 | 链上 | 保证流程和额度变化可追溯。 |
| 发票关键要素、内容指纹、流转、作废申请与作废记录 | 链上 | 支持真实性核验、责任追踪和可审计的作废审批。 |
| 报销单状态、材料摘要哈希、支付状态 | 链上 | 防止重复报销，记录审批过程。 |
| 登录密码 | 本机 `accounts.json` | 仅保存加盐哈希，不上链。 |
| 发票图片/PDF、支付截图、结项报告原件 | 链下 | 当前只记录材料说明或哈希；生产环境可接入对象存储/IPFS。 |
| OCR 云服务密钥 | 本地 `.env` | 不提交至 Git 仓库。 |

## 七、关键业务流程

### 7.1 项目与报销主流程

```text
项目组成员创建项目草稿
  → 提交立项审核
  → 审核通过，项目进入“执行中”并获得资金池额度
  → 存证关联项目的发票
  → 提交报销单
  → 审核通过，额度冻结
  → 财务确认支付，计入已支付金额
  → 申请结项
  → 结项审核通过
```

### 7.2 发票可信存证与核验流程

```text
手工填写 / OCR 辅助识别
  → 人工确认发票字段
  → 后端生成 SHA-256 内容指纹
  → 链码校验唯一性与关联项目状态
  → 发票及首次流转记录写入 Fabric
  → 查询详情或输入指纹进行核验
```

### 7.3 跨组织流转流程

```text
当前责任人发起交接
  → 校验接收账号已注册且岗位为流转员
  → 校验接收组织与账号归属一致
  → 更新当前责任人和所属组织
  → 追加不可覆盖的流转记录
```

### 7.4 项目组作废申请流程

```text
项目组成员对本人项目关联发票填写作废原因
  → 链码校验项目归属、发票状态并记录“待审核”申请
  → 本组织开票员查看申请与原因
  → 批准：发票状态变为“已作废”，不可再报销
  → 或驳回：保留原发票和审核意见，成员可补充后再次申请
```

## 九、项目特色与创新点

1. **项目资金池与发票报销联动**：不是孤立的发票上链，而是将项目预算、冻结额度、已支付金额和发票报销关系纳入统一链上流程。
2. **业务组织与 Fabric 组织分层建模**：既能在网页中灵活登记学校、内部项目组、外部协作组织，又如实保留课程网络只有两个 Fabric MSP 的技术边界。
3. **可选跨组织责任交接**：普通报销流程无需人为增加流转环节；发生真实交接时，再通过流转员记录跨组织责任变化。
4. **OCR + 人工确认的可信录入方式**：OCR 降低发票录入成本，但不让模型自动上链，保证最终上链信息由用户确认。
5. **可核验的数据指纹机制**：系统通过 SHA-256 指纹验证展示内容是否与链上存证一致，直观体现区块链存证价值。
6. **可审计的作废申请机制**：项目成员提出业务申请、开票员保留最终作废权，兼顾协作效率和票据状态控制。
7. **面向用户的明确错误提示**：对重复发票、超预算、关联项目错误、已作废发票、权限不足等情况返回可理解的业务提示。

## 十一、后续改进方向

1. **真正动态扩展联盟组织**：为外部组织自动化或半自动化完成 Fabric CA 注册、证书签发、Peer 部署、通道加入和背书策略更新。
2. **多方背书策略**：对跨组织流转、结项确认或大额支付设置 Org1 与 Org2 共同背书，进一步体现联盟链多方共治。
3. **附件可信存储**：将发票原件、支付凭证、结项报告存入 MinIO、对象存储或 IPFS，链上记录文件哈希和访问地址。
4. **真实身份与单点登录**：接入学校统一身份认证或企业 IAM，并为每位用户签发独立 Fabric 身份证书，替代课程网络中的代表性测试证书。
5. **更丰富的财务规则**：支持多发票合并报销、分期支付、预算调整申请、不同科目额度与自动预警。
6. **移动端与消息通知**：提供移动端适配、待办提醒、审核通知和异常告警。
7. **OCR 质量优化**：接入票据版式识别、发票真伪查验接口，并结合规则与人工复核提高复杂票据识别准确率。

## 十二、运行方式

在项目根目录执行：

```bash
./scripts/start-network.sh
./scripts/deploy-chaincode.sh
./scripts/start-app.sh
```

浏览器访问 `http://localhost:8080`。新建网络会部署 `invoice` v2.0；当前测试网络若仍为 v1.9 / Sequence 1，应先执行 `./scripts/upgrade-chaincode-v2.0.sh`，再重启应用。详细操作可参阅 [系统使用手册.md](系统使用手册.md)。
